A project is worked by seven agents, one job each, defined in `.claude/agents/`. The role files name no project, no directory and no stack: the loop's prompt says which project and which checkout, and each role reads that project's conventions from the claim envelope and `get_guidance` (TP-147). They check each other so no work approves itself, and each asks of anything it does: which key goal does this move, and by how much (`key-goals`)?

**The loop.** Each hand-off is a record in the tracker, so any of them can be picked up cold:
1. **Strategist** plans the next batch from the last digest's Goals served / Not touched, the project memory, the waiting findings, and the lessons that have come due: `scripts/loop.py` counts the `lesson` tickets into every strategist step's reason, naming by key each one at `PROMOTE_AT` (3) occurrences or more — the ones in triage as well as the open ones, because an AI-filed lesson waits in triage for a human and the count it has already reached is real there (TP-285) — and the plan turns each into a ticket for a mechanical check — a test, a lint rule, a script or a gate line — or a guidance rule when no check can catch it, closing the lesson when that ticket is done (TP-187).
2. **Approver** approves the plan, or sends it back. A first send-back goes to the **Strategist**, who fixes what the Approver's comment asks and records `accepted` on the eval ticket, which hands the plan back for review; a second send-back stops the loop for Joel. Before accepting, it guards every refactor in the batch: rule 21 will not let a refactor be done without a gate criterion linked to a confirmed tripwire, so the Approver finds the existing test that pins the behaviour being moved, registers it as a tripwire if needed and attaches it as that criterion (`.claude/agents/approver.md` point 7) — or sends the plan back to add the test first. It never confirms the tripwire, which is on the Only Joel list below: an unconfirmed guard gets a needs-joel ticket, the refactor goes last in the batch, and the loop stops there naming it until Joel confirms. The Approver is the one step that can send a plan back, so `scripts/loop.py` reads the plan against two of the rules above and names any gap in the `approver-accept` step's own reason rather than trusting the role file to remember it: `promotion_note` lists the lessons at `PROMOTE_AT` or more that no non-eval ticket's title or description cites, since a promotion is a ticket for the lesson and the eval names the batch rather than the work (TP-286); `guard_note` names a refactor whose gate tripwire is unconfirmed and that is either not last before the eval — the rest of the batch should be worked while Joel is asked, not behind him — or has no open needs-joel ticket naming that tripwire by id or `test_ref`, which is rule 7.4 recurring three times as lesson TP-281 (TP-288). Each ends "send it back".
3. The **loop** records the before-review itself, with no agent: the memory it starts from and `git diff --shortstat` since that memory's commit (`scripts/lib/before_review.py`). Reading the code is the reviewer's (step 6), once, after the batch is built.
4. The builders work the tickets in order — except that a refactor reaching the front of the queue still unguarded does not go to a builder: `scripts/loop.py` names an `approver-guard` step instead, the **Approver** does step 2's guarding then and there, and only then is a builder sent in.
5. Before a batch's eval ticket is worked by the **evaluator**, the loop settles both halves of stale state, neither of which costs an agent. First the code: it reads `GET /api/version` and compares both halves — the commit the process was launched at and the newest migration it carries — with its own checkout, and restarts a process that is behind through `scripts/dev.sh api`, the one launch path, waiting `LOOP_API_WAIT` seconds (default 90) for the endpoint to report HEAD. Restarting the API by hand after a migration was the single thing that stopped the loop most often, and a process left behind created an orphan batch a newer rule already forbade (TP-175, TP-257). A process with no `/api/version` answers `unknown` and counts as behind, because that endpoint is newer than any process lacking it. The commit it ends up serving goes into the evaluator's prompt, so the eval's resolution names the version it measured (goal 9). The same check runs after a `merge` step whose own diff touches `api/`, which is the moment a running process stops serving main. Then guidance: the loop runs `scripts/guidance-check.sh`, because an eval read against guidance the code has moved under judges the batch by a document nobody has re-read: a report whose every failing line is `STALE` becomes a **doc-review** step, where a builder re-reads each document named against `git diff <its pin>..HEAD -- <its paths>`, corrects it, PUTs each body it read and re-pins only those with `guidance-check.sh --accept-only` (never `just guidance --replace`, which re-pins every document, TP-283), and the loop then decides again; any other failure — a served body differing from its file above all — stops the run instead, because a re-pin would paper it over (TP-258, slots 5, 7 and 8). The **evaluator** then runs the gate, the tests that replaced the demo scripts, the verdicts and a cleanup pass; the cleanup pass fails a batch that grew in net **non-test** lines unless a decision with evidence says why — a test line is reported beside the code it covers and is not charged against the ceiling (TP-212). That decision is the eval's own (Joel, 2026-10-18): the reviewer may record it in step 6, and otherwise the evaluator judges the growth against the batch's brief, with the measurement the loop took just before its step in its prompt. It accepts the growth citing that `scripts/batch-size.sh` figure and what the brief needed the lines for, or leaves the eval open naming what should be cut; growth the brief did not ask for is a finding. One decision citing a measurement at or above the final net still covers it. A separate Approver step for this, `approver-size`, used to run here and stalled FS batches 2–4 at their evals, so it is gone. The cleanup pass carries one more check of the same shape (TP-189): a batch whose diff touches `.claude/agents/*` or guidance fails unless a `record_decision` on the eval ticket cites the digest's guidance-score line for each revision it changes, or an `eval.sh` A/B run on 3 past tickets — prompts and guidance are the harness every later batch runs on, so one changed on a hunch is the change nothing would notice. An edit that only corrects a document to match the code is exempt (Joel, 2026-10-16); its decision cites the code instead. So is an edit a planned ticket in the batch asks for, which the plan's approval covers (Joel, 2026-10-18); its decision cites that ticket. The evaluator records either itself.
6. The **reviewer** (`.claude/agents/reviewer.md`, the one Opus role besides a roadmap proposal) runs once per batch, **when its work tickets are built and before step 5's eval**. It is where the rigour is paid for, once, instead of on every ticket: it reviews the batch's whole diff for correctness, structure, readability and how easy it is to debug, fixes what it finds and deletes what is bloated, duplicated or dead in `review:` commits on the batch branch, corrects the guidance the batch moved (so the eval's doc-review rarely has anything left to do), accepts the batch's remaining growth when the net is still above zero, citing the `scripts/batch-size.sh` figure the loop measured before its step (the loop measures, not the agent: a connected project's checkout has no copy of the script, and FS's first batch went unmeasured) (it built none of it; otherwise the evaluator judges it), keeps the project's reuse register (`REUSE.md`) current for every reusable piece the batch touched, holds the code to `engineering-principles`, and every fourth review reads the whole codebase rather than only the diff (Joel, 2026-10-19). It writes the after-review, which becomes the memory. Its step's prompt lists the tool calls that failed more than once while the batch was built, counted from the run's step logs by `scripts/lib/step_errors.py`; each is a lesson candidate, filed as a `lesson` ticket unless one already covers it (TP-190).
7. The **Narrator** writes the report and finishes the batch.
8. The **Approver** signs the checkpoint. (The merge either side of it is the loop's own `merge` step, `scripts/batch-merge.sh` — no agent, no tokens.)
9. The Strategist plans again.

**Models.** Every role runs on Sonnet except the reviewer (Opus) and the Strategist's proposal of a whole roadmap, which `loop.sh` runs with `--model opus`: one decision there steers many batches. Each step's cost lands in the ledger (`LOOP_LEDGER`, read with `just cost`).

**Running the loop.** `just loop` runs the steps one agent at a time until something says stop. `./scripts/loop.sh --dry-run` only prints the next step and why. `--project KEY` (or `LOOP_PROJECT`) works that project: its newest unarchived roadmap, its tripwires, its `needs-joel` tickets, and its `repo_path` as the agents' working directory; with no project it works the API's default project on this checkout. `scripts/loop.py where` settles project, roadmap and checkout before a run starts and refuses, naming the problem, when it cannot; `scripts/loop.py next` decides each step from the tracker alone; `scripts/loop.sh` runs it:
- `claude -p --agent <role>`, with the role file passed as its definition (`--agents`, built by `scripts/lib/agent_def.py`) because `--agent` alone looks in the working directory and a connected project's checkout holds no role files, under `--permission-mode dontAsk`, so a tool the role was not given is denied rather than prompted for. A role file's `tools:` line is the whole allow list; the two builders have none, so `loop.sh`'s fallback applies: the editing tools plus `cd`, `git`, `just`, `go`, `gofmt`, `npm`, `npx`, `node`, `curl`, `python3`, the repo's own `scripts/`, the file commands a build needs (`mkdir`, `rm`, `mv`, `cp`, `touch`, `which`; the first real FS builder was stopped by a temp file it could not delete) and read-only shell (TP-132, TP-140). Under `dontAsk` every part of a compound command has to be listed, which is why `cd *` is in it;
- **each role authenticates as itself** (TP-316): its credential is a file named after it in `TICKETING_TOKEN_DIR` (default `~/.config/ticketing/agent-tokens`), and `loop.sh` puts it in that step's MCP headers as `Authorization: Bearer` and exports the same token as `TICKETING_TOKEN`, so an agent's own `curl` — the Approver's GraphQL accept — sends what its MCP calls send. A role with no file sends nothing, which is local mode and how every run worked before. Issuing the credentials is Joel's (**Only Joel**), and no role ever borrows another's;
- what that list does not tell you, checked from inside a builder step (TP-154): the editing tools do arrive — `Write` and `Edit` work, on the checkout and on the session's own scratchpad, so the standing note's "write it to a file and pass it by path" is advice a builder can follow (`.git/` is not writable, so a commit message goes under `.scratch/`). `go` and `gofmt` are entries that cannot fire: Go is on `PATH` only inside `just` (`Justfile` line 4), so bare `go` is "command not found", and naming the binary by its absolute path is denied — as is any command reading a path outside the checkout, `ls /tmp` included. Run this project's toolchain through `just`;
- every step's prompt names the project and its checkout, and carries the same standing note, because `dontAsk` refuses shell expansions (`$VAR`, `$?`, `$(...)`) and heredocs whatever the allow list says — and a command whose form it cannot match (a `( )` subshell, a `2>/dev/null` redirection, an `||` fallback) is refused even when every program in it is allowed, which the first real FS builder misread as the whole shell being denied and stopped (FS-4); the note says to write commands plainly and treat a refusal as the form's, not the shell's: write multi-line text to a file under `.scratch/` and pass it by path (`git commit -F .scratch/<file>`, `python3 .scratch/<file>`), and chain with `&&` rather than testing `$?`. The note names that directory and not only the trick, because told just to pass a path batch 16's steps wrote six commit messages into the repo root and left them there (lesson TP-334); `.scratch/` is gitignored, so what one step writes never turns up in the next step's `git status`;
- never skip-permissions, because this is the real repository;
- each step capped at `LOOP_STEP_BUDGET_USD` (default 5), with its tokens posted onto the ticket's claim, and the plan's five-hour and seven-day windows read out of the step's own log into `LOOP_USAGE_FILE` as it ends, so what is left of Joel's plan costs no extra call to know;
- **a ticket worked in another checkout has its gate recorded by the loop**, not by its builder (TP-346). `scripts/run-checks.sh` lives in this checkout, and a path outside the one the step was given is denied under `dontAsk`, so after a builder step whose `REPO` is not this checkout `loop.sh` runs the script itself, from here. It runs that ticket's own command checks in `REPO`, so `gate_passed` is the worked project's own gate and never ticketing's, and it leaves out this corpus's staleness scan, which is about code that project does not have. A red gate is printed and the run carries on, because the batch's evaluator is what judges it. An eval ticket is not gated this way — it is planned with no command checks (`service/plans.go`), its gate being the commands in its description — and a ticket worked in this checkout stays its builder's to record, as it always was.

**What stops it.**
- A run pauses after `LOOP_BATCHES` finished batches (default 3). That is the default budget, so Joel sees progress between runs.
- It stops outright:
  - when the roadmap is checkpointed stop — but *not* when it is merely complete: a finished roadmap goes to the Strategist as "propose the next roadmap (create_roadmap)", and that step ends the run, because a run works the one roadmap it resolved before it started (TP-183);
  - when the Approver sends the same plan back a second time (the first goes back to the Strategist);
  - when a step fails;
  - when an API the loop restarted still does not report this checkout's HEAD within `LOOP_API_WAIT` (default 90 seconds), naming both commits and the log to read (TP-257). Carrying on would mean an eval whose verdicts are about code the process recording them does not have, which is how one batch's `gate_passed` was lost for good (TP-211);
  - when the guidance check fails for anything other than a stale pin — a served body differing from its file above all, or a line this was not written for — because re-pinning would bury it, and a stale pin is the only kind a doc review can honestly fix (TP-258);
  - when the same step comes up twice with nothing changed;
  - at `LOOP_MAX_STEPS`;
  - when the seven-day window of Joel's plan is at or above `LOOP_USAGE_LIMIT` (default 0.6, a fraction), naming the percentage and when the window resets. That window cannot be waited out, and a batch cut off mid-ticket by the limit is the most expensive failure the loop has, so it stops cleanly between steps instead. The five-hour window at the same limit is otherwise not a stop but a `wait` step: the run sleeps until that window resets and carries on, slowing down rather than ending. Every step's reason ends with both figures — `(usage: 5h N%, week N%, seen Xm ago)`, which is how `--dry-run` shows them — and a loop that has recorded nothing yet reads as `(usage: unknown)`, which never stops a run;
  - while an open ticket in the batch it would work next is tagged **`needs-joel`**. That tag is how an agent asks for the human. One tagged anywhere else is named in the step's reason ("waiting on Joel, not blocking: TP-x") and the run carries on, so a blocker that is not in the way costs nothing.

**Steering it.** A checkpoint of `stop` or `adjust`, a `needs-joel` ticket the batch being worked has reached (one placed after the work it judges waits for that work), or plain Ctrl-C. The tracker holds all the state, so stopping is always safe and the next `just loop` resumes where the record is. `scripts/test_loop_run.py`, in `just test`, proves the orchestration by running it with fake agents.

**Only Joel.** These moves are his. No agent attempts one, and no agent keeps its own copy of this list — it is written here once and pointed at from everywhere else:
- confirming, or re-confirming, a tripwire
- creating a tag
- moving main, or rewriting history outside a batch merge
- credentials and accounts
- where data lives outside this machine
- spending

An agent that needs one of them files a `needs-joel` ticket with a numbered **What you do** section and carries on with what it can (TP-240). Everything else it does itself: agent housekeeping — re-reading a document, re-pinning a tripwire's hash, syncing a file to what is served, retiring a plan nobody ever started — is never Joel's and never lands in his triage. An agent that resolves a finding closes it with the evidence, and the Approver dismisses one still sitting in triage on its delegation, so Joel is never asked to close a ticket about a problem that is already gone.

**The Approver is separate on purpose.** A planner that approves its own plans measures nothing. The Approver accepts batches and signs checkpoints over GraphQL, the human's transport, under its own `approver` credential, so the record shows the delegation rather than impersonating Joel. The delegation **is** that credential now, not a string somebody typed: with login on an `X-Actor: approver (delegated by joel)` header is ignored, and the record says whichever actor the token the step carried belongs to. `checkpointBatch` has a second use that is not a sign-off, though: `stop` on an unfinished plan batch none of whose tickets has started retires it (rule 16), and that is housekeeping, not a judgement on work. The agent whose ticket says to retire one does it on the same transport under its own actor, as TP-175's builder recorded `backend-builder (TP-175)`; signing a *finished* batch's checkpoint stays the Approver's alone. It never approves a plan it wrote, and it stops for anything on the **Only Joel** list — which a plan's triage tickets are not: accepting those is its delegated move. What is Joel's waits in Needs you, and he can overrule any checkpoint.

**A supervising session is not the Approver.** The `approver-accept`, `approver-guard` and `approver-checkpoint` steps belong to `just loop` and to nothing else. A session supervising a run holds only the `claude-code` credential, so an accept or a checkpoint from it would be recorded under that actor or refused outright; with login on, what used to be a blocked permission is structural (TP-314). Such a session that cannot start the loop files a `needs-joel` note naming the exact mutation and its arguments rather than attempting one, and widening a permission allow-list to get round this is Joel's.

**Every write says which role made it, and no agent types that in.** The actor comes from the credential the step carries, so the history shows which role did what whether or not the agent thought about it; in local mode, with no credentials file, it still comes from the `X-Actor` header. An `actor` argument on an MCP tool is accepted and ignored, so that a client written before this is not refused (TP-318) — no agent needs to pass one, and passing one changes nothing. A decision or review with no role behind it cannot be judged later.

**Adding or changing an agent.** Keep it to one job, list only the tracker tools it needs, say which goals it guards and exactly what it hands back, and keep it project-neutral: the project comes from the prompt and the conventions from `get_guidance`, so stack-specific text belongs in that project's guidance rather than in a role file. Two guards in `api/internal/app/agents_test.go` fail `just test`: `TestEveryAgentIsWellFormedAndNamesOnlyRealTools` if an agent names a tool the server does not register, uses the tracker without reading `key-goals`, or writes without naming its actor; and `TestNoAgentHardCodesAProjectOrItsPaths` (TP-147) if a role file names a project, one of a checkout's directories, a build target, a stack tool or a language-specific guidance slug. They are deliberately two functions: the first is a confirmed tripwire, so editing it would change its hash and clear the confirmation.

**The Narrator's report is required.** A batch planned with reviews cannot finish without a summary in five sections: What was added, Why, What it achieved, Where in the code, How it moves the goals (rule 25). The digest is what the record says; the report is what it means, for a reader who will not open the diff.
